# AURORA VISION — المعمارية | Architecture

## 1. لماذا وحدتان (`:core` و `:app`)؟

المحرك كله (اكتشاف، محاذاة، تمثيل، جودة، بحث، مقاييس) موجود في **وحدة JVM خالصة** لا تعرف
شيئًا عن Android. السبب عملي: البيئة التي يُطوّر فيها المشروع لا تحتوي على هاتف ولا محاكي،
ووحدة JVM خالصة تسمح بتشغيل **الكود الإنتاجي نفسه** على الحاسوب في CI، مقابل النماذج الحقيقية،
ومقارنته رقميًا بمرجع مستقل مكتوب بـ Python/NumPy.

```
:app  (Android)  ──►  :core  (JVM)  ──►  ONNX Runtime (API واحد على المنصتين)
   UI/Compose            RgbImage, math, detect, embed, quality, search, pipeline, metrics
   Room/DataStore
   CameraX / PhotoPicker
```

`onnxruntime-android` تُوفَّر وقت التشغيل في `:app`، و`onnxruntime` (JVM) وقت الاختبار؛
والكود نفسه يستخدم `ai.onnxruntime.*` فقط. هذا ما يجعل ادعاء «النموذج يعمل» قابلًا للتحقق آليًا.

## 2. تدفّق البيانات

```
Uri/File
  └─ ImageStore.decode()        BitmapFactory + EXIF + downscale(1600px) + SHA-256
      └─ RgbImage               (ByteArray RGB، بلا اعتماد على Android)
          └─ AnalysisPipeline.analyze(request, listener)
              ├─ 01 VALIDATION   أبعاد ≥64px، ورفض الصور المتجانسة (فشل فك ترميز)
              ├─ 02 DETECTION    YuNetDetector → letterbox(640, بلا تكبير) → YuNetDecoder → NMS
              │                  + refineOnCrop للوجوه < 220px
              ├─ 03 QUALITY      SFaceEmbedder.align (112×112) → QualityAnalyzer
              ├─ 04 EXTRACTION   embedding 128D (L2) للوجوه التي اجتازت البوابة
              ├─ 05 SEARCH       SearchService + EmbeddingIndex
              ├─ 06 RANKING      تحقّق من ثبات الترتيب وعدم التكرار
              └─ 07 REPORT       AnalysisReport (قابل للتسلسل) + أزمنة كل مرحلة
```

كل `StageProgress` يُرسَل **بعد** انتهاء العمل الفعلي، والأزمنة تُقاس بـ `System.currentTimeMillis`
حول كل مرحلة وتُخزَّن في التقرير. لا يوجد مؤقّت تجميلي في أي مسار.

### الحالات النهائية (`MatchVerdict`)

| الحالة | متى | ماذا يُعرض |
|---|---|---|
| `CANDIDATES_FOUND` | يوجد تشابه ≥ العتبة | مرشّحات + تحذير أن التشابه ليس هوية |
| `NO_RELIABLE_MATCH` | البحث اكتمل ولا شيء بلغ العتبة | أفضل النتائج بدرجاتها الحقيقية |
| `QUALITY_REJECTED` | الوجه لم يجتز بوابة الجودة | أسباب الرفض، **بدون** أي درجة تشابه |
| `NO_FACES_DETECTED` | لا وجه | إرشاد لصورة أوضح |
| `NO_REFERENCE_DATA` | القاعدة فارغة/بلا سجلات متوافقة | دعوة لإضافة صور |
| `FAILED` | فشل تحليل (ملف تالف) | السبب النصي |

## 3. قرارات تقنية وأدلّتها

### 3.1 letterbox 640 بدون تكبير
YuNet ثابت الدخل 640×640 ويُدرَّب على وجوه 10–300 px. تكبير الصور الصغيرة يستهلك زمنًا
ويُضيّع تفاصيل دون فائدة. لذلك `ImageOps.letterbox(..., allowUpscale = false)`.

### 3.2 تمرير ثانٍ مكبَّر للوجوه الصغيرة (refine)
عندما يكون الوجه < 220 px، يُعاد تشغيل الكاشف على قصاصة مكبّرة (حتى ×3) لتحديد نقاط أوضح،
فتتحسّن المحاذاة. القياس (LFW، أزواج متطابقة/مختلفة):

| | AUC | EER | زمن الاكتشاف (سطح مكتب) |
|---|---|---|---|
| مُفعّل | 0.9982 | 1.84 % | 21.9 ms |
| معطّل | 0.9967 | 2.68 % | 9.8 ms |

القرار: مُفعّل (تحسّن ملموس في EER مقابل ~12 ms على الحاسوب).

### 3.3 المحاذاة: Umeyama بصيغة مغلقة للأبعاد الثنائية
OpenCV يستخدم SVD. في 2D لتحويل تشابهي (conformal) الحل الأمثل مغلق:
`α = Σ(d·p)/Σ|p|²`، `β = Σ(dy·px − dx·py)/Σ|p|²`، `θ = atan2(β, α)`، `scale = √(α²+β²)/Σ|p|²`.
قُوبلت النتيجة مع مرجع SVD بدقة 1e-14 (اختبار انحدار في `UmeyamaTest`).
> ملاحظة: أثناء التطوير كان هناك خطأ إشارة في `β` أدّى إلى تدوير المحاذاة في الاتجاه الخطأ،
> كشفه اختبار التكافؤ مع المرجع. أُصلح ودُوّن هنا كي لا يتكرر.

### 3.4 المعالجة المسبقة لـ SFace: RGB في 0..255
`blobFromImage(img, 1, Size(112,112), Scalar(0,0,0), true, false)` في OpenCV: **بدون قسمة على 255**
وبدون طرح متوسط، مع تبديل القنوات إلى RGB. القسمة على 255 (وهي عادة شائعة) تُفقد التمثيل تمامًا:
قيس التدهور في مرحلة التحقق (تشابه جيب التمام ≈ 0.04) وأُصلح.

### 3.5 البحث: شامل ومقصود
تمثيلات الوحدة تُقارن بضرب نقطي. 20,000 سجل = 2.56M عملية ضرب (اختبار وحدة يقيس الزمن ويشترطه
< 500 ms على JVM). الفهرس يُخزَّن كمصفوفة `FloatArray` متصلة لتسلسل الذاكرة، والترتيب حتمي
(تنازلي ثم بمعرّف السجل) ليكون قابلًا لإعادة الإنتاج. ما بعد ~50k سجل يحتاج فهرسًا تقريبيًا،
وهذا مذكور كحدّ معروف بدلًا من ادعاء قابلية توسّع غير مقيسة.

### 3.6 بوابة الجودة: ترفض ولا تخمّن
اقتُرحت عتبات من توزيعات مقاسة (وجوه LFW سليمة مقابل تدهور صناعي موثّق):
`sharpness ≥ 29.4`، `brightness ≥ 21.2`، `contrast ≥ 17.3`، `face ≥ 48 px`، `|yaw| ≤ 0.35`،
`|roll| ≤ 30°`. نسبة رفض الوجوه السليمة المقاسة: 1.27 %.

**قيد معروف:** مقياس Laplacian للحدّة غير موثوق للوجوه الصغيرة جدًا لأن تكبير المحاذاة يعيد
إدخال ترددات عالية (مقيس: وجوه مموّهة في قصاصات صغيرة تسجّل 200–440 بدلًا من ~5). لذلك
(أ) أُضيف هامش 15 % لاستبعاد حواف الحشو، (ب) لا تُقدَّم أي نتيجة كموثوقة عند جودة ضعيفة،
(ج) القيد موثّق في `docs/EVALUATION.md` وليس مخفيًا.

## 4. طبقة البيانات (Room)

```
face_records      وجه واحد لكل سجل + embeddingEncrypted (BLOB) + groupId يجمع وجوه الصورة
search_sessions   ملخص البحث + reportJson (التقرير الكامل)
search_matches    صف لكل نتيجة مرتبة (CASCADE على الجلسة)
```

* التكرار: SHA-256 للصورة + فهرس فريد `(imageSha256, faceIndex)`.
* `modelKey` على كل سجل: البحث يستثني سجلات نموذج مختلف ويُبلّغ عن عددها.
* التشفير: AES-256-GCM بمفتاح `AndroidKeyStore` (غير قابل للتصدير)، يُخزَّن `IV || ciphertext`.
* لا `fallbackToDestructiveMigration`: تغيير المخطط يتطلب ترحيلًا صريحًا كي لا تُمسح
  القوالب البيومترية بصمت.

## 5. الواجهة (Compose)

* RTL مفروض عبر `LocalLayoutDirection` كي تبقى العربية صحيحة على أجهزة بإعدادات LTR.
* لوحة ألوان داكنة (ليل/سماوي/بنفسجي معتدل)، شبكة تقنية مرسومة بـ Canvas (لا صور ثقيلة).
* طبقة المسح الضوئي تظهر **فقط** أثناء مرحلة قيد التنفيذ.
* إطار رقمي حول الوجه + علامات النقاط الخمس مرسومة من إحداثيات الكاشف نفسه.
* الحركات عبر `animateFloatAsState`/`rememberInfiniteTransition` (بلا تأثير على زمن التحليل).

## 6. الاختبارات والتحقق

| المستوى | ماذا يتحقق | كيف |
|---|---|---|
| تكافؤ رقمي | الاكتشاف/التضمين/الجودة/الحدود | golden vectors من مرجع Python (`tools/reference`) |
| نموذج حقيقي | النماذج تُحمَّل وتعمل | `:core` tests تشغّل ONNX Runtime فعليًا |
| منطق البحث | الترتيب، العتبة، الاستثناءات، 20k سجل | `SearchServiceTest`, `EmbeddingIndex` |
| المقاييس | AUC/EER/FAR/FRR | `VerificationMetricsTest` |
| التخزين | ترميز القوالب، تسلسل التقرير، سلامة الأصول | `:app` tests |
| البناء | APK يحتوي النماذج والمعايرة و`libonnxruntime.so` | خطوة CI تتحقق من محتوى APK |

## 7. ما لم يُنفَّذ (بصراحة)

* لا تشغيل على جهاز/محاكي في هذه البيئة (الواجهة والكاميرا لم تُجرَّبا بصريًا).
* لا فهرس تقريبي (ANN) — غير مطلوب في هذا الحجم.
* لا نسخ احتياطي مُدار للمستخدم (معطّل عمدًا لبيانات بيومترية).
* لا دعم لصورة تحتوي أكثر من ~20 وجهًا (حد `maxFaces`).
